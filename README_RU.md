# Полный конвейер OTSO для анализа геомагнитной полутени

Этот каталог содержит активную тестовую версию конвейера, общий модуль переносимых путей и исходный файл MATLAB `data/penumbra_boundaries.mat`.

Назначение программы — построить для каждой комбинации географических и угловых координат индивидуальное окно жёсткости, выполнить трассировку OTSO, классифицировать траектории как разрешённые или запрещённые и вычислить метрики внутренней структуры полутени.

Принятая во всём конвейере конвенция:

- `raw_filter == 1` — разрешённая траектория (`white`, белая);
- `raw_filter != 1` — запрещённая траектория (`black`, чёрная).

## 1. Состав каталога

Основной конвейер:

1. `rigidity_window_grid.py` — загрузка, очистка и линейная интерполяция исходной сетки MATLAB.
2. `5d_raw_scan.py` — этап 1: формирование плана и первичный расчёт OTSO.
3. `5d_check_closure.py` — этап 2: проверка замкнутости окон.
4. `5d_rerun_open_cases.py` — этап 3: повторный расчёт только открытых окон в пределах допусков.
5. `5d_check_closure_final.py` — этап 3b: окончательная проверка замкнутости после объединения результатов.
6. `5d_finalize_classification.py` — этап 4: итоговая классификация физических случаев и ячеек графиков.
7. `5d_compute_penumbra_metrics.py` — этап 5: вычисление метрик полутени.

Построение графиков:

8. `plot_metric_validation_common.py` — общие функции, цветовые шкалы, сетки и оформление.
9. `plot_geographic_metric_validation.py` — один географический heatmap `latitude–longitude`.
10. `plot_geographic_dR_total_validation.py` — географический heatmap для выбранной высоты.
11. `plot_angular_metric_validation.py` — один угловой heatmap `azimuth–zenith`.
12. `plot_angular_validation.py` — альтернативная/проверочная версия углового графика.
13. `export_graficos_vkr.py` — пакетный экспорт всех настроенных heatmap в PNG.
14. `plot_barcode_compare.py` — визуализация и сравнение barcode отдельного случая.
15. `pipeline_paths.py` — единое переносимое разрешение каталогов run и графиков.

Исходные данные:

- `data/penumbra_boundaries.mat` — грубая четырёхмерная оценочная сетка границ жёсткости с осями `(latitude, longitude, zenith, azimuth)` и массивами `RlNet`, `RuNet`.

Старые скрипты второй низкоэнергетической экстензии и диагностики в пакет не включены: текущая упрощённая схема использует одну ограниченную допусками повторную трассировку, после которой незамкнутые случаи исключаются.

## 2. Требуемое окружение

Этапы, запускающие OTSO, проверяют, что установлена версия OTSO `1.2.19`. Имя и абсолютный путь виртуального окружения не фиксируются, поэтому проект переносим между компьютерами.

Рекомендуемая установка:

```bash
conda env create -f environment.yml
conda activate otso_1219
PYTHON=python
```

Также необходимы `numpy`, `pandas`, `scipy` и `matplotlib`; их версии описаны в `environment.yml` и `requirements.txt`.

## 3. Что настраивает исследователь перед запуском

### Интерполяционная сетка

В `rigidity_window_grid.py` задаются новые узлы:

- `LAT_OUT` — широты;
- `LON_OUT` — долготы;
- `ZEN_OUT` — зенитные углы;
- `AZ_OUT` — азимуты.

Интерполяция линейная, без экстраполяции. Новая точка принимается только тогда, когда все вершины соответствующей четырёхмерной ячейки исходной сетки имеют допустимые данные. `NaN`, открытая верхняя граница `Ru = 55 GV` и некорректные большие инверсии границ не превращаются в физические окна.

### Физические и вычислительные параметры этапа 1

В верхней части `5d_raw_scan.py` задаются:

- `GRID_SOURCE = "matlab_interpolated"`;
- `INTERPOLATED_H0_VALUES` — фиксированная высота или набор высот; сейчас `(400.0,)` км;
- дата и время в `DATETIME_PARAMS`;
- параметры интегрирования и частицы;
- шаг жёсткости `DR`;
- начальные запасы окна `WINDOW_MARGIN_LOW_GV`, `WINDOW_MARGIN_HIGH_GV`;
- полные пределы допуска `TOTAL_TOLERANCE_LOW_GV`, `TOTAL_TOLERANCE_HIGH_GV`;
- нижний физический предел `RIGIDITY_FLOOR_GV`;
- `MAX_CASES` — необязательное ограничение числа реально рассчитанных случаев;
- `STRATIFIED_TEST_CASES` — уменьшенный тестовый план; значение `None` означает полный интерполированный план;
- `RESUME_RUN_ID` — продолжение прерванного запуска.

Файл MATLAB не содержит оси высоты. Поэтому высота не интерполируется: исследователь задаёт её в `INTERPOLATED_H0_VALUES`. Для каждой выбранной высоты создаётся копия допустимой четырёхмерной сетки.

## 4. Этапы обработки

### Этап 1 — интерполяция и первичная трассировка

Запуск:

```bash
cd /путь/к/otso_full_pipeline
$PYTHON 5d_raw_scan.py
```

`rigidity_window_grid.py` читает `data/penumbra_boundaries.mat`, очищает исходные `RlNet/RuNet` и линейно интерполирует нижнюю и верхнюю оценки границ. Для каждой допустимой комбинации `(lat, lon, h0, zenith, azimuth)` формируется один физический `case_id` и индивидуальное окно OTSO.

Вертикальная избыточность удаляется на физическом уровне: при `zenith = 0°` и `180°` все азимуты описывают одно направление и ссылаются на канонический случай с `azimuth = 0°`. Ячейки для отображения могут сохранять нужные координаты и ссылаться на этот же физический случай, поэтому одна и та же траектория не рассчитывается многократно.

Основные выходные файлы:

- `case_plan.csv` — уникальные физические случаи, координаты, оценочные границы, начальные окна и пределы допуска;
- `plot_cell_plan.csv` — координатные ячейки будущих графиков и ссылка каждой ячейки на `case_id`;
- `interpolated_rigidity_windows.csv` — результат интерполяции;
- `raw_barcodes_initial.csv` — первичные barcode OTSO;
- `case_status_initial.csv` — статус выполнения каждого случая;
- `run_parameters.txt`, `runtime.json` — параметры и время запуска.

Каталог запуска создаётся автоматически внутри локального `runs/5d_raw_default_requested_scans/`. Его полный путь выводится в терминал и записывается в локальный `active_run.txt`.

### Этап 2 — первичная проверка замкнутости

Скрипт `5d_check_closure.py` не запускает OTSO. Он читает `case_plan.csv` и `raw_barcodes_initial.csv` и проверяет по `EDGE_N = 10`, что низкожёсткий край содержит десять запрещённых точек, а высокожёсткий край — десять разрешённых.

Возможные состояния: `closed`, `open_low`, `open_high`, `open_both` и состояния ошибки/отсутствия данных. Для открытых окон скрипт берёт пределы `R_tolerance_min` и `R_tolerance_max` непосредственно из `case_plan.csv`; он не знает и не должен знать, как была получена интерполяция.

Выходы:

- `closure_report_initial.csv`;
- `open_cases_for_rerun.csv` с точными интервалами необходимого расширения;
- `closure_summary.txt`.

### Этап 3 — ограниченный повторный расчёт

`5d_rerun_open_cases.py` запускает OTSO только для интервалов из `open_cases_for_rerun.csv`. Расширение никогда не выходит за пределы допуска, заданные на этапе 1. Длинные интервалы делятся на блоки до `1.5 GV`; каждый вызов имеет безопасную минимальную длину `0.10 GV`, что снижает риск нативных сбоев OTSO.

Первичный barcode не перезаписывается. Новые точки сохраняются отдельно, затем объединяются по `(case_id, R)`.

Выходы:

- `extension_plan.csv`;
- `raw_barcodes_extensions.csv`;
- `case_status_extensions.csv`;
- `raw_barcodes_merged.csv`;
- `extension_errors.csv`, `duplicate_conflicts.csv`, `merge_summary.txt`, `extension_runtime.json`.

Если список расширений пуст, этап корректно создаёт объединённый результат без лишних вызовов OTSO.

### Этап 3b — окончательное замыкание

`5d_check_closure_final.py` повторяет критерий `EDGE_N = 10` для `raw_barcodes_merged.csv`.

Выходы:

- `closure_report_final.csv`;
- `remaining_open_cases_after_extensions.csv`;
- `discarded_cases_after_tolerance.csv`;
- `closure_status_transitions.csv`;
- `closure_summary_final.txt`.

Текущая политика проста: если случай остаётся открытым после разрешённого расширения, он исключается. Таким образом оценочная сетка служит для оптимизации времени, но немного неточная оценка не отбрасывает полезный случай до повторного расчёта в пределах допуска.

### Этап 4 — итоговая классификация

`5d_finalize_classification.py` читает план, объединённые barcode и окончательный отчёт замыкания. Если существует `raw_barcodes_merged_final.csv`, он имеет приоритет; в текущей схеме нормально используется `raw_barcodes_merged.csv`.

Замкнутый случай получает политику `compute_metrics`. Случай, не замкнувшийся в пределах допуска, получает `discarded_after_tolerance`, политику `exclude` и не подменяется нулевым физическим результатом.

Выходы:

- `final_case_classification.csv` — одна строка на физический случай;
- `final_plot_cell_classification.csv` — классификация, перенесённая на все ячейки отображения через `case_id`;
- `closure_report_after_low2.csv` — историческое имя итогового отчёта, сохранённое для совместимости;
- `remaining_unresolved_cases_final.csv`;
- `final_classification_summary.txt`.

### Этап 5 — метрики полутени

`5d_compute_penumbra_metrics.py` использует только случаи с политикой `compute_metrics`, анализирует последовательность белых и чёрных точек и вычисляет:

- `dR_total` — полная ширина области полутени;
- `dR_white`, `dR_black`, `dR_gray`;
- `f_gray`;
- `N_100`, `N_400`;
- дополнительные диагностические числа интервалов и полос.

Исключённые случаи остаются `NaN`; ноль не используется вместо отсутствующего физического результата.

Выходы:

- `penumbra_metrics_by_case.csv`;
- `penumbra_metrics_by_plot_cell.csv` — главный вход всех heatmap;
- `penumbra_interval_details.csv`;
- `penumbra_metrics_summary.txt`.

## 5. Последовательность запуска этапов 2–5

После этапа 1 остальные скрипты автоматически читают каталог из `active_run.txt`. Поэтому обычный порядок запуска выглядит так:

```bash
$PYTHON 5d_check_closure.py
$PYTHON 5d_rerun_open_cases.py
$PYTHON 5d_check_closure_final.py
$PYTHON 5d_finalize_classification.py
$PYTHON 5d_compute_penumbra_metrics.py
```

Для выбора другого существующего запуска можно явно задать:

```bash
export PENUMBRA_RUN_DIR=/полный/путь/к/созданному/run_...
```

Для размещения всех новых запусков вне репозитория используется `PENUMBRA_RUNS_DIR`.

Каждый следующий этап следует запускать только после успешного завершения предыдущего. Предыдущие CSV не перезаписываются; каждый этап создаёт новые файлы в том же каталоге запуска.

## 6. Построение heatmap

Все скрипты графиков читают `PENUMBRA_RUN_DIR/penumbra_metrics_by_plot_cell.csv`. Метрика выбирается переменной `FIELD_NAME`; допустимы `dR_total`, `dR_white`, `dR_black`, `dR_gray`, `f_gray`, `N_100`, `N_400`.

### Географический график

В `plot_geographic_metric_validation.py` исследователь вручную фиксирует:

- `PLOT_H0` — высоту, сейчас 400 км;
- `PLOT_ZENITH` и `PLOT_AZIMUTH` — направление, сейчас вертикаль `(0°, 0°)`;
- `FIELD_NAME` — отображаемую метрику.

Оси heatmap: longitude и latitude.

```bash
$PYTHON plot_geographic_metric_validation.py
```

### График для выбранной высоты

`plot_geographic_dR_total_validation.py` также строит карту latitude–longitude, но явно выбирает `PLOT_H0`. Несмотря на историческое имя файла, через `FIELD_NAME` можно выбрать любую поддерживаемую метрику. Сейчас доступна высота 400 км, потому что именно она включена в план этапа 1.

```bash
$PYTHON plot_geographic_dR_total_validation.py
```

### Угловой график

В `plot_angular_metric_validation.py` или `plot_angular_validation.py` исследователь вручную задаёт фиксированные `PLOT_LAT`, `PLOT_LON`, `PLOT_H0` и метрику. Оси heatmap: azimuth и zenith.

Текущие значения координат соответствуют Асунсьону только как примеру фиксированной точки для двумерного среза. Это не отдельный этап и не специальный физический случай. Выбранные `PLOT_LAT/PLOT_LON` должны точно присутствовать в интерполированном плане. В текущей регулярной выходной сетке точных координат Асунсьона нет; для проверки можно, например, выбрать `PLOT_LAT = -30.0`, `PLOT_LON = 300.0`, либо изменить сетку этапа 1 так, чтобы она содержала требуемую точку.

```bash
$PYTHON plot_angular_metric_validation.py
```

### Пакетный экспорт

`export_graficos_vkr.py` использует те же типы срезов и экспортирует PNG для всех семи метрик. Перед запуском следует проверить константы `GEO_DIRECTIONS`, `ALT_H0_VALUES`, `ANG_H0`, `ANG_LAT`, `ANG_LON`.

Каталог вывода лучше задать явно:

```bash
export PENUMBRA_PLOT_OUTPUT_DIR=/полный/путь/к/каталогу/графиков
$PYTHON export_graficos_vkr.py
```

### Barcode отдельного случая

`plot_barcode_compare.py` показывает структуру разрешённых/запрещённых интервалов одного случая. Случай выбирается настройками в верхней части скрипта.

```bash
$PYTHON plot_barcode_compare.py
```

## 7. Важные замечания

- Полный интерполированный план для текущих настроек содержит 21 462 уникальных физических случая и 24 912 ячеек отображения. Полный расчёт OTSO ещё не запускался.
- В коде нет абсолютных путей конкретного компьютера. Этапы 2–5 используют `PENUMBRA_RUN_DIR` или локальный `active_run.txt`.
- OTSO 1.2.19 иногда аварийно завершает нативный worker. Изоляция каждого расчёта в отдельном subprocess позволяет продолжить запуск; неуспешные случаи фиксируются в status/error CSV и могут быть повторены через механизм resume.
- Heatmap являются двумерными срезами пятимерного результата. Поэтому для географической карты фиксируются высота и углы, а для угловой карты — широта, долгота и высота.
- `NaN` означает отсутствие надёжного физического результата и не должен смешиваться с физическим нулём.

GitHub Actions в `.github/workflows/validate.yml` проверяет синтаксис и интерполяцию MATLAB при каждом `push` и `pull_request`, но намеренно не запускает длительный расчёт OTSO.
